# Release 0.1.0 backend status

This is the living status page of the Rust backend of release 0.1.0, the designer slice: a weapons editor (ranged and melee) that always writes vanilla definitions, an optional Combat Extended (CE) patch generator, and a minimal manager crate for settings and sources, with the CLI as the interim front end. The scope, exit criteria and deferred items are in [roadmap section 2.1](../roadmap.md#21-010-release-designer-slice); the decisions are D-083 to D-094 in the [decision register](../architecture/decision-register.md) and [ADR 0035](../adr/0035-in-house-json-database.md), [ADR 0036](../adr/0036-release-scope-and-backend-first.md) and [ADR 0037](../adr/0037-vanilla-default-optional-ce-patch.md).

Status: backend complete for the slice, hardened and measured in the second round, completed in the third round (clone flow and gaps), UI not started | Last updated: 2026-10-05

## How to read this page

1. Each row is a requirement group, not a single test. A group is done when the behaviour of its requirement ids is covered by passing tests and, where the group touches the user's data, by a run on the owner's machine. Where one id of a group is only partly covered the row says partial and names it.
2. States: done, partial (works, with a named gap), deferred (outside 0.1.0 by decision; the reason is in the row).
3. Evidence is either a test name, a gate result, or a summarised command transcript from section 3. Real install runs used `RIMSTUDIO_GAME_DIR`, `RIMSTUDIO_WORKSHOP_DIR`, `RIMSTUDIO_CE_DIR` (the Combat Extended workshop folder) and `RIMSTUDIO_CUSTOM_DIR`, only read, and wrote only into temporary folders. The CLI runs used a throw-away home and XDG folders, so nothing was written into the owner's real app data.
4. The ids were not checked one by one. Evidence is at the level of the group; the test files named in each row carry the individual ids.
5. The owner rules apply to every row: vanilla by default with CE only as an optional patch (D-085), no SQL and no new storage engine (D-083), no licence headers or files (D-088), no RimWorld or CE value tables in the repository (R11).

### 3.6 Round 2 findings in the CLI that are not defects of the engine

- A rating can read "unreliable" next to an error under 35 percent (for example bulk 33 percent) because the 80th percentile error is 80 percent or more; the text view does not say that. A UI should show the P80 figure too.
- `--set ce.toolPenetration.0.tool=NAME` and `.blunt` or `.sharp` are needed to answer a penetration for a designed weapon. The help of `convert` and `plan` now documents the answers file shapes and this key with examples (third round).
- `designer new --strength typical` without `--from` used to leave the parent, projectile and cost list empty; in the third round `designer_structure_defaults` fills them from the nearest reference weapon as suggestions, and `new --from DEFNAME` is a real clone.

## 4. Deviations from the docs

- The designer suggests the CE block of a new weapon (`ce-suggest`, `--accept-suggestions`) but never fills the ammo set or the weapon tag class, and the toggle is never turned on by a suggestion (D-096). Shot spread and magazine size are rated unreliable on the owner's install and stay asks.
- Unusable estimates of the convert flow are asked (D-095) rather than written; `AskItemDto` now carries the reason and the rejected estimate (`reason`, `suggestion`), and the plan text of an open question names the reason.
- `designer_quiz_back` is a registry action; the terminal quiz uses it for back.
- `lint ce` is partial (section 2). The CLI has no `--data-dir`; tests isolate state through `HOME` and the XDG variables.

## 5. Known limitations

- Estimates rest on 17 to 19 converted weapons of one install; with another library the ratings may be mostly rough or unreliable. The candidate ranking of ammo sets is a heuristic over tags and one damage number. Bows sit in the gun pool and lower the gun figures.
- Converting a mod of many guns asks about two penetration questions per gun plus magazine and spread; one answers file entry can now cover a whole weapon family (key from `convert scan`, family = kind, first weapon tag and default projectile), but there is no wildcard matching on defNames.
- The atomic writer leaves a named temporary file inside the mod folder during a write that survives a hard crash; the Workshop publish staging must exclude it. The app installs the game write fence into the project environment when the sessions are built (and for `project_create`), see items toolkit section 15.11.
- Bows, crossbows, grenades, launchers, turrets and apparel are not converted; bows and crossbows (a bow or crossbow weapon tag or class, or an arrow or bolt projectile) are listed by the convert scan as unsupported-kind with the reason "CE bow conversion is not available in 0.1.0".
- A gun clone points at the projectile definition of its source, so a different damage changes the readouts but not the written definition until the clone gets its own inline projectile (the diff and the clone notes say so). A weapon of the user's own project cannot be cloned yet, and a source with a Combat Extended conversion is refused.
- Magazine size, sights and tool details cannot be read from a vanilla definition, so they are guessed or must be answered with `--set overrides.<field>=value`.
- The convert scan now uses `reader::is_weapon_def` for melee weapons too; on this install the candidate count did not change (115), because no mod of the owner holds a tagless weapon.
- The reference armor of the owner's install is 0, 0.92 and 1.2, not the prototypes' 0, 0.55 and 1.0 (documented in item balance math 14.8); stuffed melee weapons are priced with the game's 2 silver guess by default.
- CEP010 and CEP015 are never checked, because no caller supplies the CE type and field tables.
- The patch operations rely on XPath attribute predicates verified only by the in-engine dry run, not by a game run. Nothing here was loaded in RimWorld itself.
- Only Linux was run. Windows and macOS behaviour, junctions and file identity (`Platform::file_id` returns none) are open.
- The terminal quiz was run by hand under a pseudo terminal against the owner's install (answers, skip, not sure, back, bad input, typed values, done) and has a pty integration test (`rimstudio-cli/tests/quiz_pty.rs`, Linux with util-linux `script`). Back calls the registry action `designer_quiz_back`.
- Test harness note: the def engine integration tests prepare their input with a helper that takes about 14 s for the install (the product path takes 15 ms); this is test only.
- Several mods of the owner's folder produce `IfModActiveAny` warnings; the folder also holds a `Config/rimstudio.project.json` from an earlier spike in one mod, which the app did not read or change.
